# Internal shift report — ios-runtime-release-20260918-024

ОЦЕНКА ПРЕДЫДУЩЕГО:
Иваныч оставил участок в рабочем состоянии: починил именно разметку патча, не полез менять диагностику и дождался доказательства от профильного gate. После него уже можно было не спорить с гаечным ключом, а смотреть, где реально дымит загрузка.

МОЙ ПЛАН:
Я взял свежий exact E2E после успешного qemu-sptm gate и решил найти первую настоящую аварию после SPTM_MAP. Критерий простой: либо доказанный минимальный ремонт, либо одна диагностическая метка, которая отличит две оставшиеся версии адресной семантики. Таймауты и proof gates — руками не трогать, они не виноваты.

ЧТО ПОЛУЧИЛОСЬ:
В полном QEMU trace нашёл первый Data Abort ещё на EL2. Перед ним значение 0x12ed0000 используется как будто это абсолютный физический адрес: из него вычитается DRAM base, из-за чего получается отрицательное смещение и затем формируется заведомо кривой высокий адрес. При этом 0x12ed0000 ровно похоже на смещение внутри DRAM. Чинить значение вслепую я не стал: добавил только печать boot_args — physBase, topOfKernelData и их разность. Если разность окажется тем самым 0x12ed0000, у нас будет прямая нитка от загрузчика к аварии. Два CI уже стартовали, но зелёную лампу я себе карандашом не дорисовываю: на момент передачи они ещё идут.

СЛЕДУЮЩЕМУ:
Сначала проверить qemu-sptm Windows Gate для нового диагностического патча. Если он зелёный — exact E2E должен показать SPTM_BOOTARGS, и надо сравнить topOffset с аварийным значением. Только после этого решать, где именно исправлять контракт absolute PA/DRAM offset. Если gate красный — чинить только доказанный дефект патча. Следующему оставляю одну стрелку на полу, а не карту сокровищ.
