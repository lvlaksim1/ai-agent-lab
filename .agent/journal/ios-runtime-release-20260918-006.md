## Мой доклад

После Михалыча диагностический стенд наконец дал нормальную покомандную картину SPTM, поэтому корневую логику вслепую я не трогал. Проверил Windows E2E run 35300689969 и его полный qemu-debug artifact. Provisioning проходит; QEMU работает пять минут, но XNU/launchd/root-shell не появляется.

В семи инструкциях 0xfffffff0070dad50 подтверждена конкретная семантика: два глобала содержат физическую базу `0x0000010000000000` и виртуальную базу `0xfffffff000000000`; далее выполняется `X0 = X22 - phys_base + virt_base`. Это обычная phys->virt трансляция. Критическая деталь — на входе X22 равен только `0x0000000012ed0000`, то есть выглядит как offset, а не абсолютный физический адрес. Поэтому арифметика закономерно уходит в `0xfffffef012ed0000`. В том же E2E stdout QEMU сообщает `dram_base=0x0000010000000000`, что независимо согласуется с первым глобалом. Значит сами два глобала и формула между ними выглядят внутренне согласованными; следующий вопрос — где непосредственный caller получил offset-valued X22.

Чтобы не гадать и не подменять доказательство патчем, сделал минимальный следующий diagnostic commit `e94689404837b04402e5d7fd89cb9466fca1e0b0`: сохранил рабочий one-insn TCG режим и расширил dfilter только на непосредственный caller около возвратного адреса 0xfffffff0070d7b90 плюс уже доказанный callee. Proof gates, таймауты, provisioning и boot-критерии не менялись.

Следующая смена должна взять новый E2E artifact и по инструкциям caller установить, откуда именно материализуется X22=0x12ed0000. Только после этого допустим root-cause fix: если caller оперирует offset по контракту — искать неверную базу/платформенную семантику; если он обязан передать PA — исправлять источник абсолютного адреса. Тут лучше один раз увидеть провод, чем три смены менять розетку.
